# 3. 已登录状态下的重启空窗期等待页 ⬜ 未开始

**本意**: 不是首次登录 VRChat(那次已经有等待页了), 而是——

**不是什么**: ❌ 不是"登录页前再加个 loading"。**交互式登录的等待页已经做完了**:
`public/index.html:244-257` 全屏遮罩 + 毛玻璃卡 + 四行步骤(验证信息→获取用户信息→获取好友信息→等待前端就绪),

**现状(为什么没覆盖)**: 等待页的触发条件写死在交互登录上 ——
`public/app.js:956-967` 只在 `loginWaiting` 为真时 `bootShow()`, 而 `loginWaiting` 只有

**要做**: ① autoLogin 阶段也发 `sync-progress`; ② 前端增加"恢复会话中"状态, 复用现有等待页;

# 13. 离线好友展开动画没了 ✅ 已修复(2026-09-28)

**本意**: 点「离线 (N)」左边那个三角展开时, 应该能看到展开过程, 而不是"啪"地一下全出来。

**关键线索是方向不对称**: 实测 **展开没有动画、收起有动画**。这个不对称就是定位的入口 ——
如果只是"动画没写", 两个方向应该一起没有。

## 实测数据(`serve-demo.js` + 浏览器逐帧采样; 离线组 77 行, 组高 4696px, 视口 720px)

> ⚠️ 采样是在**无头浏览器**里做的: 它的合成/滚动时序与真机不同, **绝对耗时只能作同一环境内的相对比较**;
> 几何量(元素高度、可见窗口)和代码事实不受影响。

点击时滚动停在页面底部 → 离线组标题在视口 y=465, **标题下方只剩 227px 是可见的**,
而组高 4696px —— 可见窗口只有组的 **1/20**。

量"揭示边界扫过可见窗口"用了多久:

| 场景 | 可见窗口 | 边界扫过可见窗口耗时 |
|---|---|---|
| 展开 | 227px | **0ms**(头一帧就扫完了) |
| 收起 | 227px | **98ms**(看得出) |
| 收起(标题挪到视口顶部, 窗口 632px) | 632px | 169ms |
| 展开(注入 `linear` 缓动做对照) | 632px | 24ms |
| 收起(注入 `linear` 缓动做对照) | 227px | **0ms**(收起也变没了) |

容器过渡本身是好的 —— 两个方向都有 13 个中间值, `grid-template-rows` 0px↔4696px 一路插值,
四组的 computed style 也完全一致(`display:grid` / `transition .3s` / `.group-inner{overflow:hidden;min-height:0}`)。
**问题不是"没有动画", 而是动画发生在了看不见的地方。**

## 根因(三层叠加)

1. **可见窗口太小: 组高 4696px vs 可见 227px(20 倍)**
   离线组贴在视口最下沿(折叠时它就在页面底部), 而展开是"从上往下揭示" ——
   边界只要走 227px 就离开屏幕了, 这只占全部行程的 **5%**。
   → **你的猜测方向是对的**: "页面此时较短"确实让它只剩一条 227px 的缝; 展开后页面变长,
   收起时整组都在屏幕上, 才有得看。
2. **缓动曲线前重后轻** `cubic-bezier(.22,.8,.3,1)`(`public/app.css:519`)
   展开时: 该扫过可见窗口的那 5% 行程**正好落在曲线最快的一段** → 头一帧过去。
   收起时: 快的部分全在屏幕外, **慢尾巴恰好发生在屏幕上** → 看得见。
   线性对照实验证明这一点: 缓动换 `linear` 后, **收起也变成 0ms** ——
   **"收起有动画"是缓动曲线给的, 不是方向给的。**
3. **行级入场动画也不补**: `markFriendsEntrance()`(`public/app.js:1047-1057`)在首屏一帧内就给
   **所有**行(包括折叠组里看不见的行)打上 `.enter`, CSS `riseIn`(`public/app.css:1059-1062`)随即播完
   —— 实测离线组 154 次 `riseIn` 全是在折叠状态下播的; 之后展开时 `row.getAnimations()` 返回 `[]`。
   于是屏幕内连"行"的变化都没有, 彻底成了瞬间出现。
   (对照: 把默认折叠的组换成「在线」→ `online(动画时折叠) = 104 次`, **谁折叠谁就白播**, 与排第几无关。)

## 修复 ✅ 已实现(`public/app.js`, 2026-09-28)

**做法: 展开折叠组时, 给组内前 31 行重放 `.enter` 入场级联。**
落点: 分组标题的 click handler —— 展开时调 `replayGroupEntrance(body)`:
`remove('enter')` → `void offsetWidth` 强制重排 → 重新编号 `--i` 再 `add('enter')`。
收起方向不补(它本来就看得见, 补了反而多一次闪)。

⚠️ **硬约束: 只补放前 `FADE_CAP + 1 = 31` 行, 不要给整组补放。** 实测(合成 5005 行的组):

| 补放范围 | 点击那一刻的同步卡顿 | 产生的动画对象 |
|---|---|---|
| 全部 5005 行 | **168ms**(明显卡一下) | 5011 个 |
| 只补放前 31 行 | **6ms**(无感) | 30 个 |

视觉上两者完全一样 —— 视口里只看得到最前面 4 行, 且 `--i` 到 31 就撞上限,
第 31 行以后延迟全是同一个 900ms, 本就没有阶梯感。

**A/B 验证**(基线副本跑 3101 / 新版跑 3100, 同一份演示数据, 每次测量前 `bringToFront`):

| 检查项 | 基线 | 新版 |
|---|---|---|
| 点三角展开时, 行上起了几个 `riseIn` | **0** | **16**(其中视口内 4 个, 动画中 opacity 0.19/0.22/0.07/0.11) |
| 展开后容器高度 | 4696px | 4696px(一致) |
| 收起 | 正常 | 正常(一致) |
| 分组数 / 行序 / 分组归属 / 前 100 行 DOM | — | **逐字节一致** |
| 21 个关键元素的几何 + 计算样式 | — | **逐项一致**(页面高度同为 5437) |

⚠️ 排查坑: 两个页面**并行**测量时, 非前台标签页的 rAF/动画会被 Chrome 节流,
基线会假性显示"0 个动画、0 个 FLIP 项"。必须在每次测量前 `page.bringToFront()` 并串行执行。

### 附带发现: 大列表的展开本来就会掉帧(与本次修复无关)

同一台机器实测(离线组, 清空残留动画后):

| 场景 | 帧数/500ms | 最大帧间隔 |
|---|---|---|
| 77 行 · 展开 | 20 | 33ms(≈60fps) |
| 77 行 · 收起 | 22 | 33ms |
| **5005 行 · 展开(现行代码, 未加任何修复)** | 16 | **117ms** |
| **5005 行 · 收起(现行代码)** | 13 | **100ms** |
| 5005 行 · 展开 + 只补放 31 行 | 12 | 100ms(在卡顿基线内, 没变差) |

原因: `grid-template-rows` 是布局属性, 过渡期间**每帧都要把整组上千行重新排版一次**;
加上列表完全不虚拟化(折叠组里的行也真实存在 DOM 里)。
现实好友量级(几十~几百)下无感, 真机上的权威结论见 **#15**(5000 人时实测"滚动都卡")。
上表的帧数据同样来自无头浏览器, 只看"同一环境内的相对差异", 别当绝对值。

## 滚动路径重构(2026-09-29, 照 kolarorz/virt-list 的思路)

**问题**(实测反馈): 快速滚动时动画会乱/消失/卡顿, 而且"好友位置变化"几乎看不到动画。

**病根**: 旧实现**每跨一行就 `innerHTML` 重建整个渲染窗口**(一次约 40 行), 而且滚动路径上
每帧都 `getBoundingClientRect` / `getComputedStyle` 强制重排。
用 MutationObserver 量出来: 滚 3000px 时节点增删 **+639 / −622**(约 10 次整窗重建)——
正在播的 CSS 动画挂在那些被删掉的节点上, 自然"啪"一下就没了。

**改法**(三条, 都是 virt-list 的核心):
1. **双层范围**: `inView`(严格可见)与 `range`(可见 ± 12 行 buffer)。先比 `inView`, 再比 `range`,
   两层都没变就**一个节点都不动**; 滚动过程中绝大多数帧 DOM 完全静止。
2. **节点复用**: 窗口平移只增删两端差集(`V.reconcileIds` + 指针式 `insertBefore`),
   中间节点原地保留 —— **DOM 节点就是动画载体, 重建即丢动画**。
3. **滚动路径零布局读取**: 列表位置与各分组标题的高度/外边距缓存在 `vLayout`,
   行高改由 `ResizeObserver` 回调更新; 滚动时只读 `window.scrollY`。

**效果**: 同样滚 3000px, 节点增删 **+639/−622 → +46/−27**(≈ 每跨一行只增删一个节点, 已是理论最小值)。
新增断言: *小幅滚动(在 buffer 内)必须复用同一个节点对象* —— 这条直接锁住"滚动不打断动画";

**位置变化动画**: 最终定为**原位淡出 → 换组 → 新位置淡入**(不依赖任何绝对位置)。
中途试过一版"幽灵飞行"(在旧位置放 `position:fixed` 的克隆行飞向新位置): 长列表里太跳,
而且和节点回收/滚动打架, 已按需求去掉。现在点「特别关注」是: 这一行在原地淡出, 淡完重绘到新分组,
若新位置在渲染窗口里就淡入, 在窗口外自然就是"淡走了"。

**验证**: 150 人与 5000 人两档都跑 `.verify/parity.js`, 白名单外零差异(几何/页高/5 个滚动位置的可见行/功能流程),
12 条动画与抖动断言全过; `npm test` **534 项**。

## 虚拟列表不变量(改动时别踩, 详细版见 `.verify/frontend-ab-brief.md` 第 8 节)

1. **行高缓存只存"带下边框"的内容高**; 每组末行少的那 1px 由模型在构建前缀和时统一扣
   —— 否则"搜索过滤后的子集"里量到的值会污染全量列表。
2. **测量到非正值必须丢弃**: 切到设置页时列表 `display:none`, 全是 0; 而且这个判断必须在
   `+1`(补末行边框)**之前**, 否则 0+1 会绕过守卫变成 1px(实测整组凭空少 60px)。
3. **任何行高变化都要让前缀和失效**, 否则占位高度用脏数据(实测某个组少一行的高度)。
4. 折叠组不渲染也不动它(它的高度是 0, 内容留给容器过渡裁剪); 切换可见性(切页/主界面显示)后要强制重算窗口。

## 其它还没做的

- **真机滚动手感确认**: 虚拟化把 DOM 从 87438 个元素降到 690, 主线程每帧的 JS 成本也早就证明是微秒级
  (见下), 但**合成/光栅开销只有在真实浏览器里才测得准**。需要在 3100(新版) 与 3101(基线) 之间体感对比。
- **列表卡片的 `backdrop-filter: blur(14px)`**: 15 万像素高的卡片每帧重模糊, 仍是潜在开销。
  只在高行数时关掉不影响正常量级观感, 但同样**无头浏览器测不出效果**, 需要真机验证。
- 折叠组内容的惰性渲染/图片延迟加载: **虚拟化之后这条已经没有收益了** ——
  折叠组现在一行都不渲染, 里面的头像自然不会请求。

## 已排除的怀疑对象(别再往这个方向查)

**自制惯性平滑滚动不是瓶颈**: 实测 `window.scrollTo` **2.7µs/次**、`scrollHeight` 读数 0.3µs/次、
两者交替(布局抖动)**3.0µs/次** —— 主线程 JS 每帧只花几微秒, 没有任何强制重排。
所以卡的是**渲染/合成**, 不是这段 JS; 也就没必要为了性能去动它(动了反而改手感)。
